# Plan 3: both sides of a hit — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** pixfx games get a whole hit: effect cues the game answers on the contact frame, creatures that move through
states when struck, attack timing that drives a pixfx-fighter body, and the Bloater, melee and moves effects to use them.

**Architecture:** Four pure modules join `pixfx-core` (`cue`, `state`, `screen`, `act`, plus `chain` for composed
effects); pixfx-fighter's `Feel` becomes the single owner of hitstop, shake, ripple and flash; effects are ported into
`pixfx-effects` with pixel parity against their JS; `pixfx-canvas` binds the new pieces and a site page ("hit lab")
shows them together.

**Tech Stack:** Rust 2024 workspace, wasm-bindgen (`pixfx-canvas`), Node for JS references, Bun for site tests,
Chrome for the page check.

**Spec:** `docs/superpowers/specs/2026-11-13-plan3-hit-design.md`

## Review Focus

1. A cue at exactly t = 0 must fire on the first update (game-factory fires `(t0 - 1e-9, t1]` on the first step);
   a missed contact-frame hitstop is the most visible bug. → Task 1 test `cue_at_zero_fires_on_first_update`.
2. A hitstop must not stall ripples and flash (they age in real time) nor the creature's carry of `hits` across
   `next`. → Task 3 test `ripple_and_flash_age_during_hitstop`; Task 2 test `carry_survives_follow`.
3. A looping state (idle, remains) never follows `next` by itself; only one-shots do. → Task 2 test
   `looping_state_does_not_follow`.
4. `from = -1` mirrors the hit side in pictures and cue x; `flip` and `from` combined must not double-mirror. →
   Task 6 parity with `--opt from=-1`, and Task 1 test `flip_mirrors_cue_x_once`.
5. Feel caps: fight hit + effect hitstop on the same frame give one freeze of the larger length, trauma ≤ 1. →
   Task 3 test `fight_and_effect_cues_share_one_freeze`.

### Task 10: Composed effects (`pixfx-core::chain`)

**Files:** Create `crates/pixfx-core/src/chain.rs`; test `crates/pixfx-core/tests/chain.rs`.

**Interfaces:**
- Produces: the port of pixelfx `src/core/chain.js`:
  - `pub enum Place { At(f64), Path(fn(f64) -> f64) }` (a number, or a function of the move's time, local space)
  - `pub struct Part { pub effect: &'static dyn Effect, pub t: f64, pub until: f64, pub x: Place, pub y: Place, pub flip: bool, pub opts: fn(&mut Options) }`
    (`until` = `f64::INFINITY` when the JS omits it; `opts` lays the part's own options over its defaults)
  - `pub struct Chain { … }` implementing `EffectState`, built by `pub fn chain(parts: &'static [Part], opts: &Options, seed: u64) -> Chain`
- Semantics exactly as `chain.js`: part i's seed is `seed + i`; on the first update where `t ≥ part.t` the part's
  instance is created **without** an update, later updates advance it; it is over once `t ≥ until` or it is done and
  not looping; draw places each live part at `(tx + sign·x(t), ty + y(t))`, flip = `sign < 0 != part.flip`, back
  layer then front, and leaves the painter's placement as it found it. Positions are computed at draw time (draw is
  `&self`), not stored.
- Cues: a chain's cues are its parts' cues shifted by `part.t`, dropping those at or after `until` (game-factory has no
  chain cues; this is pixfx's own addition, documented in the module doc).
